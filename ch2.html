    2.1Map representations, path planning algorithms

    Path planning needs a map, and the map decides the algorithm

    Path planning finds a collision-free sequence of configurations from a start to a goal, usually minimising a cost such as length, time or risk. Before any algorithm can run, the free space must be represented. Three representations dominate:

    CriterionOccupancy gridTopological graphContinuous (polygons)
    Built fromRange sensors directly (Ch 7)Places and connections, by hand or segmentationCAD drawings or line extraction
    MemoryGrows with area / resolution squaredTinyGrows with number of edges
    PlannerDijkstra, A*, D*Graph searchVisibility graph, Voronoi, cell decomposition
    WeaknessResolution-dependent, jagged pathsNo metric detail for obstacle avoidanceHard to keep up to date

    Review question 1 of TLO1 asks you to explain map representation in exactly these terms.

    Configuration space: planning for a point instead of a robot

    Planning for a robot of finite size is simplified by the configuration space (C-space): the space of all robot poses. Each obstacle is grown by the robot's shape to form a C-space obstacle; the robot then becomes a point. For a circular robot of radius rrr the growth is simply a dilation of every obstacle by rrr, which is what the inflation layer of a ROS costmap does. For a rectangular robot the C-space is 3D (x,y,θ)(x, y, \theta)(x,y,θ) because the grown shape depends on heading.

    Definition to write
    The free configuration space CfreeC_{free}Cfree​ is the set of poses at which the robot does not intersect any obstacle. Path planning is the search for a continuous curve in CfreeC_{free}Cfree​ from qstartq_{start}qstart​ to qgoalq_{goal}qgoal​.

    Dijkstra: expand in order of cost-to-come

    On a grid treated as a graph (cells are nodes, neighbours are edges with cost 1 or 2\sqrt22​), Dijkstra's algorithm keeps a priority queue ordered by the cost-to-come g(n)g(n)g(n). It repeatedly removes the cheapest node, marks it closed and relaxes its neighbours: if g(n)+c(n,m)<g(m)g(n) + c(n,m) < g(m)g(n)+c(n,m)<g(m), set g(m)g(m)g(m) and the parent pointer. When the goal is removed from the queue, following parents backwards gives the optimal path.

    1. Initialise g(start)=0g(start) = 0g(start)=0, all others infinity; push start.
    2. Pop the node with the smallest ggg; stop if it is the goal.
    3. For each free neighbour, relax the edge and push it if improved.
    4. Repeat; reconstruct the path from the parent pointers.

    Dijkstra is complete and optimal but explores uniformly in all directions, like a wave front, because it has no idea where the goal is.

    A*: add a heuristic that points towards the goal

    A* orders the queue by f(n)=g(n)+h(n)f(n) = g(n) + h(n)f(n)=g(n)+h(n), where h(n)h(n)h(n) estimates the remaining cost. If hhh never overestimates (it is admissible), A* still returns the optimal path, and if hhh is consistent each node is expanded at most once. On an 8-connected grid the Euclidean or octile distance is admissible. Setting h=0h = 0h=0 recovers Dijkstra; inflating it (f=g+whf = g + w hf=g+wh, w>1w > 1w>1, weighted A*) expands fewer cells but gives paths up to www times the optimum.

    InteractiveGrid planners: Dijkstra, A*, weighted A* and greedy
    Try it
    Draw a wall that forces a U-shaped detour and compare the expanded cells of A* and greedy best-first. Greedy uses only hhh: it is fast but falls into the pocket and returns a longer path.

    D*: replanning when the map changes

    A robot discovers obstacles as it moves. Replanning from scratch with A* after every change is wasteful because most of the previous search is still valid. D* (Stentz, 1994) and its simpler successor D* Lite (Koenig and Likhachev, 2002) search backwards from the goal and, when edge costs change, repair only the affected part of the search tree. On Mars, the rover navigation software of NASA's rovers used D*-family field planners for exactly this reason: terrain is only revealed as the rover drives.

    Review question 2 asks you to explain the range of algorithms from Dijkstra to A*, D* and RRT. A concise answer: Dijkstra is uninformed optimal search; A* adds an admissible heuristic to reduce expansions while keeping optimality; D* adds efficient incremental repair for changing maps; RRT abandons the grid altogether and samples continuous C-space, which scales to high dimensions.

    2.2Sampling-based path planning, path smoothing

    Why sample: grids explode in high dimensions

    A grid with 100 cells per axis has 10210^2102 cells in 2D, 10310^3103 for (x,y,θ)(x, y, \theta)(x,y,θ), and 101210^{12}1012 for a 6-joint arm. Sampling-based planners avoid building this grid: they draw random configurations, keep the collision-free ones and connect them with short local motions. They are probabilistically complete: if a path exists, the probability of finding it tends to 1 as samples grow.

    • PRM (probabilistic roadmap): sample many configurations once, connect nearby pairs, then answer many queries by graph search. Suits static environments with repeated queries.
    • RRT (rapidly-exploring random tree): grow a tree from the start. Sample qrandq_{rand}qrand​, find the nearest tree node qnearq_{near}qnear​, step a distance ϵ\epsilonϵ towards qrandq_{rand}qrand​ to get qnewq_{new}qnew​, and add it if the edge is collision-free. A small goal bias (sample the goal itself 5 percent of the time) speeds convergence.
    • RRT*: when adding qnewq_{new}qnew​, choose the cheapest parent among neighbours in a radius and rewire neighbours through qnewq_{new}qnew​ if cheaper. RRT* is asymptotically optimal.

    RRT in action

    InteractiveRRT and RRT* sampling-based planning
    Try it
    Switch between RRT and RRT* with the same number of samples. RRT* paths straighten as samples increase; plain RRT paths do not.

    Runtime: nearest-neighbour search dominates

    Review question 5: every RRT iteration must find the nearest existing node. A linear scan costs O(N)O(N)O(N), so building a tree of NNN nodes costs O(N2)O(N^2)O(N2). With a kd-tree and uniformly random samples, the tree stays approximately balanced, so both inserting a point and querying the nearest neighbour take O(log⁡N)O(\log N)O(logN) expected time (its depth). Building the whole tree is then O(Nlog⁡N)O(N\log N)O(NlogN). The worst case of a single insertion into a badly unbalanced kd-tree is O(N)O(N)O(N), but uniform random insertion order makes this unlikely.

    Review question 6 asks what else matters besides asymptotic complexity:

    • Collision checking usually dominates wall-clock time; use bounding volumes, lazy checking (check edges only when they lie on a candidate path) and a coarse-to-fine resolution along each edge.
    • Narrow passages are rarely sampled; use bridge or Gaussian sampling biased towards obstacle boundaries.
    • Memory grows with the tree; prune nodes that cannot improve the solution.
    • Variance of runtime: randomised planners have unpredictable latency; bound iterations and fall back to a safe stop.
    • Path quality: raw RRT paths are jerky; post-process with shortcutting and smoothing.

    Path smoothing: the robot cannot drive a staircase

    Grid and RRT paths have sharp corners that a wheeled robot cannot follow at speed. A simple and widely taught smoother moves each interior waypoint yiy_iyi​ to balance two goals: stay near the original waypoint xix_ixi​ and stay near its neighbours:

    yi←yi+wdata(xi−yi)+wsmooth(yi−1+yi+1−2yi),y_i \leftarrow y_i + w_{data}(x_i - y_i) + w_{smooth}(y_{i-1} + y_{i+1} - 2y_i),yi​←yi​+wdata​(xi​−yi​)+wsmooth​(yi−1​+yi+1​−2yi​),

    iterated until the change is small, with start and goal fixed. A large wsmoothw_{smooth}wsmooth​ straightens the path; a large wdataw_{data}wdata​ keeps it close to the collision-checked original.

    Pitfall
    Smoothing can pull a path into an obstacle at a tight corner. Always collision-check the result, or smooth inside the inflated costmap. Alternatives that respect robot dynamics directly are cubic splines, Bezier curves and state-lattice planners that use only feasible motion primitives.

    2.3Planning at different length scales

    One planner cannot do everything

    A delivery robot in a hospital must choose which lift to take (hundreds of metres, decided rarely), plan a corridor path (tens of metres, replanned when blocked), dodge a trolley (a few metres, tens of times per second) and hold wheel speeds (centimetres, hundreds of times per second). No single algorithm is both globally optimal and fast enough for the last layer, so planning is hierarchical.

    In ROS 2 Nav2 this appears as a behaviour tree (mission logic), a global planner plugin (NavFn or Smac, grid A*/hybrid-A*), a local controller plugin (DWB, which is a dynamic window approach, or MPPI) and the ros2_control wheel controllers.

    Variations of the path-planning problem

    Review question 3 asks you to discuss variations of the planning problem. The core problem assumes a known, static map, a point robot and a single goal. Real systems relax each assumption:

    VariationWhat changesTypical method
    Unknown or partially known mapObstacles discovered while movingD* Lite, frontier exploration
    Dynamic obstaclesObstacles move; time becomes a dimensionVelocity obstacles, space-time A*, DWA
    Kinodynamic constraintsCurvature, acceleration limitsHybrid A*, state lattices, kinodynamic RRT
    CoverageVisit every point, not one goalBoustrophedon decomposition (cleaning, mowing)
    Multi-robotRobots are obstacles to each otherPrioritised planning, conflict-based search
    Uncertainty-awarePose is uncertain; minimise riskCostmaps with inflation, belief-space planning

    TLO3 asks you to select sensors and implement an algorithm. A sensible first build for a 3- or 4-wheeled robot: wheel encoders and an IMU for odometry, a 2D LiDAR for mapping and obstacles, A* on an inflated occupancy grid for the global path, and a feedback or DWA controller for tracking (review question 4). The planner tool on the previous topic runs exactly this A* on a grid.

    2.4Uncertainty and error propagation in robotics

    Where robot uncertainty comes from

    Review question 1 (and ESA question 1c) asks for the factors that lead to robot uncertainty. Thrun, Burgard and Fox list five; write each with an example:

    1. Environments are unpredictable: people walk, doors open, pallets are moved.
    2. Sensors are limited by physics (range, resolution, field of view) and corrupted by noise; a LiDAR cannot see through glass or beyond 30 m.
    3. Robot actuation is imprecise: motor control noise, wheel slip, wear, uneven floors and backlash mean commanded and actual motion differ.
    4. Models are approximations: a point-mass, flat-floor, rigid-wheel model is never exactly true.
    5. Computation is limited: algorithms approximate (finite particles, discretised grids, linearisation) to meet real-time deadlines.
    Why it matters
    A robot that ignores uncertainty acts on its best guess as if it were true. A robot that represents uncertainty can hedge: slow down when unsure, look for landmarks, or refuse an unsafe action.

    Error propagation: how uncertainty flows through a function

    If an input xxx has covariance Σx\Sigma_xΣx​ and y=f(x)y = f(x)y=f(x), first-order error propagation linearises fff around the mean with its Jacobian F=∂f/∂xF = \partial f/\partial xF=∂f/∂x:

    Σy≈F Σx FT.\Sigma_y \approx F\,\Sigma_x\,F^T .Σy​≈FΣx​FT.

    For dead reckoning with pose xt=(x,y,θ)x_t = (x, y, \theta)xt​=(x,y,θ) and noisy controls u=(v,ω)u = (v, \omega)u=(v,ω) with covariance MMM, the pose covariance evolves as

    Σt=Gt Σt−1 GtT+Vt Mt VtT,\Sigma_t = G_t\,\Sigma_{t-1}\,G_t^T + V_t\,M_t\,V_t^T,Σt​=Gt​Σt−1​GtT​+Vt​Mt​VtT​,

    2.5Probabilistic robotics

    The key idea: represent uncertainty explicitly with probability

    Probabilistic robotics replaces the single best guess with a probability distribution over all possible states, called the belief:

    bel(xt)=p(xt∣z1:t, u1:t),bel(x_t) = p(x_t \mid z_{1:t},\ u_{1:t}),bel(xt​)=p(xt​∣z1:t​, u1:t​),

    the probability of state xtx_txt​ given all measurements zzz and controls uuu so far. Perception and action both become probabilistic models: a measurement model p(zt∣xt)p(z_t \mid x_t)p(zt​∣xt​) and a motion model p(xt∣ut,xt−1)p(x_t \mid u_t, x_{t-1})p(xt​∣ut​,xt−1​). Everything in Chapters 3-7 is built from these two ingredients combined by Bayes' rule.

    Two advantages are decisive in practice. First, robustness: the robot degrades gracefully when sensors fail or the map is wrong, instead of committing to a wrong answer. Second, the method scales from a one-dimensional door to full SLAM with the same mathematics. The price is computation: distributions over continuous spaces must be approximated.

    Probabilistic robots in the field

    Real-life example: museum tour guides and self-driving cars
    The RHINO (Bonn, 1997) and MINERVA (Smithsonian, 1998) tour-guide robots, built by the authors of the course textbook, used Markov and Monte Carlo localization to navigate crowded museums for thousands of hours. Stanley, Stanford's winner of the 2005 DARPA Grand Challenge, used probabilistic sensor fusion to classify terrain as drivable. Every modern AMR stack, including Nav2's AMCL node, descends from these systems.
    Discuss
    A robot vacuum that bumps into things and turns randomly has no belief at all. Why does it still clean a room? What would a belief let it do better? (Coverage time, and knowing when it has finished.)

    Random variables, densities and the Gaussian

    A robot's obstacle detector has p(hit | occupied) = 0.85 and p(hit | free) = 0.15. The prior probability that a cell is occupied is 0.3. Compute the posterior after one hit, after two independent hits, and after a hit followed by a miss.

    Marking scheme
    MarksExpected answer content
    3One hit: 0.85*0.3 / (0.85*0.3 + 0.15*0.7) = 0.708.
    3Two hits: prior 0.708 -> 0.932.
    3Hit then miss: p(miss|occ) = 0.15, p(miss|free) = 0.85: 0.300.
    1The result equals the prior 0.3 because the sensor is symmetric, p(hit|occ) = p(miss|free) = 0.85, so the likelihood ratios 0.85/0.15 and 0.15/0.85 cancel.
    Q2.10L3 ApplyCO2TLO1PI 1.3.1Topics 2.610 marks

    Two independent Gaussian estimates of a robot's x-position are N(2.0, 0.8^2) m from odometry and N(3.0, 0.5^2) m from a beacon. Compute the mean and standard deviation of their normalised product, and the probability, under the fused estimate, that the robot is beyond 3.0 m.

    Marking scheme
    MarksExpected answer content
    4mean = (2.0*0.25 + 3.0*0.64)/(0.64 + 0.25) = 2.719 m.
    3sd = sqrt(0.64*0.25/0.89) = 0.424 m.
    3P(x > 3.0) = 1 - Phi((0.281)/0.424) = 0.254.
